# Nine-section task template

This template is generated inside the existing managed region. Old descriptions stay outside it as history. It is a proposed replacement for earlier planning guidance, not additional execution authorization.

## 1. User outcome and review evidence

Name the consultant's task and the observable improvement. Cite the exact review section/quotation and V6 requirement. Distinguish historical observations from current source inspection.

## 2. Priority and reason

Give the proposed Multica priority and its rationale. State whether it blocks correctness, the principal journey, usability, or later validation. A batch number is not itself a reason for high priority.

## 3. Prerequisites and execution order

List hard prerequisites with the exact output and accepted completion evidence needed. Keep recommended sequence and parallel work separate. Shared files require an ownership decision before parallel editing. Do not make the index depend on children as an implementation prerequisite.

## 4. Bounded deliverable

Name one reviewable output. A planning task delivers a decision contract, a feature task delivers user-observable behavior, and a verification task delivers a bounded evidence report. Split independent outcomes before implementation if necessary.

## 5. Scope and protected behavior

State allowed behavior changes, non-goals, and invariants. Protect original source/history, unknowns, explicit preview/adoption, manual edits and original graders. List protected paths. If source inspection reveals another required file or product change, stop that expansion and produce a revised scope preview instead of silently broadening it.

## 6. Source map and evidence

For each file name the exact repository-relative path, current symbol/line, role, hash, and reason. Distinguish planned edits from reading and verification. Record unknown/new-file design explicitly. Do not guess migration filenames or call a partial map complete. Planning tasks can have no edit files and read-only evidence only.

## 7. Observable acceptance

Cover normal progress, refusal/keeping existing work, failure, and recovery. Each case names the starting context, action, expected artifact/state change, preserved state, and verification kind. Keep unsupported thresholds and decisions open.

## 8. Verification, evidence and open decisions

Name targeted behavior checks, real surface actions, any real-model semantic gate, and user acceptance separately. Specify the evidence expected without claiming it already exists. Real calls and recordings need their own approved budgets. Document decisions that block starting, not only questions to ask at the end.

## 9. Start gate and completion

Before implementation require approved scope/product rules, accepted hard prerequisites, a bounded current source map, testable acceptance and explicit permission to start. A task in backlog or a synchronized description is not permission. Completion requires recorded results and human review rather than auto-done. The gate command is read-only and never starts an Agent.
