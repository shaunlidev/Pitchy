## 1. Outcome

The Agent UX P0 slice makes the application report Agent activity from authoritative workflow state instead of a loose client-side loading flag. It also gives interrupted actions a recoverable UI and preserves the original command identity when the user retries an uncertain Agent action.

This is an engineering implementation result. It is not browser acceptance, live-model quality validation, customer validation, production readiness, or deployment evidence.

## 2. Product decisions preserved

- Pitchroom v6 remains the product and design authority.
- An Agent guess must not silently become the user's working direction.
- User work and previously confirmed state must remain available after an Agent failure.
- A UI may say an action completed only when the persisted workflow confirms completion.
- A transport or storage interruption has an unknown outcome until the application refreshes authoritative state.
- Retrying an uncertain Agent action must reuse the original `commandId` so the server can deduplicate it.
- Technical details may be inspectable, but the primary recovery UI must explain the user consequence and available next action.

## 3. Implemented in this slice

### Truthful Agent state

- Added a single workspace UX-state derivation layer for queued, running, completed, failed and cancelled activity.
- Reconciled active client requests with persisted workflow runs and project events.
- Prevented a completed positioning run from continuing to display `Agent working`.
- Allowed a persisted running workflow to appear as running after refresh, even without an in-memory request.

### Recovery and retry

- Split initial workspace-load errors from action errors.
- Added a structured `Action interrupted` recovery card for unknown outcomes.
- The card states that existing work is preserved and that the requested result is not yet confirmed.
- Added retry, refresh and current-step review actions.
- Retrying an uncertain Agent action reuses its original `commandId` and request body.
- Request IDs and technical details remain available without leading the recovery experience.

### Adjacent runtime repair

- Rebound Drizzle's query map when Next.js hot-module replacement leaves a cached client bound to an older schema object.
- This addresses failures such as `Cannot read properties of undefined (reading 'findFirst')` caused by stale `db.query.<table>` entries.

## 7. Known risks and open questions

- The recovery contract is covered deterministically but still needs isolated browser acceptance for copy, focus order, mobile layout and actual retry behavior.
- A recovered request needs browser-level confirmation that the same command is not applied twice.
- P1 must not add a second competing navigation system. It should derive one clear next action from the same authoritative workspace state.
- Capability guidance must describe what the Agent can do at the current step; it must not promise unsupported autonomy.
- Steering should happen at safe checkpoints and preserve explicit Apply boundaries from v6.
- The advanced Agent inspector should remain inspectable without becoming the primary user workflow.

## 8. Recommended next scope: Agent UX P1

Implement one coherent next-action and steering layer, without redesigning the whole product:

1. Derive one primary next action from workspace phase, Agent state and unresolved user decision.
2. Make locked destinations explain what prerequisite is missing and offer the relevant action.
3. Add concise capability guidance at each step: what the Agent can do now, what it needs from the user, and what it will not change without approval.
4. Add steering checkpoints before positioning is applied and before a deck is generated.
5. Keep manual edit, source access, original framing, history and undo behavior intact.
6. Add deterministic component tests first, then run browser acceptance only in isolated synthetic state with separate authorization for any recording.

P1 acceptance signals:

- At every stable screen state, there is one visually primary next action.
- A locked tab is either not interactive or explains its exact prerequisite; it never looks broken.
- During Agent work, the user can see the current phase and the next safe steering point.
- Before a consequential change, the user can review/edit and explicitly Apply it.
- Failure and refresh never erase confirmed work or silently duplicate an action.
